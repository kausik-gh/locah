# FOUNDER REFINEMENT — BOOKINGS

Bookings should behave like a familiar, high-quality booking system.

Do not overcomplicate it.

The important requirement is:

ONE BOOKING ENGINE
+
BOOKING MODE
+
RESOURCE / PROVIDER / CAPACITY
+
BUSINESS RULES
+
PAYMENT REQUIREMENT
+
ROLE
+
CHANNEL

→ CORRECT BOOKING EXPERIENCE.

Supported current booking modes:

- appointment
- table
- stay
- class
- rental
- site visit
- event date

Do not build separate SalonBooking, HotelBooking, TableBooking, etc.

Use one Booking domain with mode-specific behavior.

================================================================
1. ONE BOOKING TRUTH ACROSS ALL CHANNELS
================================================================

A customer may book through:

- Website
- Marketplace
- WhatsApp
- phone
- AI Receptionist
- front desk / staff
- owner Workspace
- Crew/provider surface where appropriate

All of them must create the SAME booking record.

Do not create:

website_bookings
whatsapp_bookings
phone_bookings
frontdesk_bookings.

Store channel/source for context, but keep one booking truth.

================================================================
2. STANDARD CUSTOMER BOOKING FLOW
================================================================

For a normal service/appointment:

Choose service
→ choose provider if applicable
→ choose date
→ show real available slots
→ choose slot
→ customer details
→ deposit/full payment if required
→ confirm
→ booking confirmation
→ reminders
→ My Activity.

If provider choice is optional:

allow:

Any available provider

or

Choose provider.

Do not force provider selection where the Business normally assigns staff itself.

================================================================
3. AVAILABILITY MUST BE REAL
================================================================

Availability should derive from:

Business opening hours
location
provider/resource schedule
service duration
buffers
existing bookings
blocked time
capacity
booking rules.

Do not show a slot just because it exists in a static timetable.

Recheck availability at final confirmation.

Use a slot lock / equivalent concurrency control so two people cannot take the
same slot simultaneously.

The canonical source explicitly requires booking commit-time slot locking.

================================================================
4. BUSINESS CONFIGURATION
================================================================

The Business should configure only what matters to that mode.

Examples:

booking horizon
minimum notice
maximum advance booking period
service duration
buffer before/after
cancellation window
reschedule window
deposit/full-payment requirement
no-show policy
provider selection
capacity
waitlist
recurrence where allowed
confirmation mode.

Do not show hotel settings to a salon.

Do not show class capacity to a table-booking-only restaurant.

================================================================
5. APPOINTMENT MODE
================================================================

Used by:

salon
spa
clinic front desk
consultant
therapist/non-clinical service
professional service
home-service consultation
other provider-based businesses.

Typical flow:

Service
→ provider / any provider
→ date
→ slot
→ optional deposit
→ confirmation.

Workspace should emphasize:

calendar
today
upcoming
waiting
cancelled
no-shows
provider schedule.

================================================================
6. CLINIC / HEALTH FRONT DESK
================================================================

Booking is strictly front-desk scheduling.

Support:

department/service
provider
date
slot
queue relationship where enabled
confirmation/reminder.

Do NOT turn Bookings into:

clinical records
diagnosis
prescriptions
triage.

AI Receptionist may book appointments but must preserve healthcare guardrails.

================================================================
7. SALON / SPA
================================================================

Support:

service
duration
stylist/provider
optional preferred provider
packages where Memberships applies
deposit where configured.

Example:

Haircut
→ Priya
→ Saturday
→ 4:30 PM
→ ₹200 deposit
→ confirmed.

================================================================
8. GYM / FITNESS
================================================================

Different booking types may coexist.

Examples:

PT session
trial
group class.

PT:
provider + time slot.

Class:
fixed session + capacity.

If Memberships is enabled:
eligibility/session-pack balance should be checked.

Booking engine must not itself own membership balance.

================================================================
9. CLASS MODE
================================================================

Used by:

gym
yoga
dance
music
coaching
education
workshops.

A class has:

session/date/time
capacity
enrolled/booked count
waitlist
instructor/resource.

When full:
offer waitlist if enabled.

If a seat opens:
the Appointment/automation layer may notify or promote according to configured
rules.

Do not overbook unless the owner explicitly allows it.

================================================================
10. TABLE BOOKING
================================================================

Restaurant/table mode should ask things relevant to table reservations:

date
time
party size
customer/contact
notes where appropriate.

Availability should account for:

table/capacity configuration
opening/service hours
existing reservations
turnaround duration where configured.

Do not make customers choose an internal table number unless the Business wants
that.

The Business may assign the actual table later.

Restaurant Workspace should show:

upcoming reservations
party size
arrival time
seated / completed / no-show state.

================================================================
11. HOTEL / STAY MODE
================================================================

Stay booking is date-range based, not slot based.

Customer flow:

check-in date
→ check-out date
→ guests
→ available room types/resources
→ select
→ rate
→ deposit/full payment if configured
→ confirmation.

The Business may configure:

room type
named rooms
occupancy
availability
deposit
check-in/out times
cancellation rule.

Do not double-book a room/resource.

Hotels/resorts in the canonical source explicitly require room types/named rooms,
date-range availability, deposits and a direct booking engine. 

Housekeeping is handled by Tasks, not Bookings.

Payment is handled by Payments.

Guest documents are handled by Documents.

Booking just coordinates the stay reservation.

================================================================
12. RENTAL MODE
================================================================

Used for:

cars
bikes
camera
tools
equipment
costumes
party gear
furniture
other reservable assets.

Customer selects:

resource/item
start date/time
end date/time
availability
deposit where required
pickup/delivery where configured.

Reservation prevents the same resource being promised twice.

Handover/return inspection belongs to Tasks/Documents/Jobs where applicable.

Damage/late fee workflow should not be embedded directly into Booking core.

================================================================
13. SITE VISIT
================================================================

Used by:

real estate
interiors
solar/site surveys
construction-related businesses.

Flow:

project/property/service
→ preferred date
→ available sales/service person
→ slot
→ confirmation
→ assignment.

This may also create/update a Lead.

Booking owns the visit slot.

Leads owns the sales relationship.

================================================================
14. EVENT DATE BOOKING
================================================================

Used by:

hall/mandapam
photographer
caterer
event venue
wedding-related businesses
other date-specific services.

The date/resource may be the scarce thing rather than an hourly provider slot.

Support:

event date
time window where required
resource/package
capacity where relevant
deposit
confirmation.

Some businesses may first require:

enquiry → quote → event booking.

Do not force instant booking if the Business uses quotation-first flow.

================================================================
15. RECURRING BOOKINGS
================================================================

Where appropriate:

weekly class
weekly consultation
recurring service slot.

Recurring setup should create/manage linked occurrences.

Allow:

edit one occurrence
cancel one occurrence
change future occurrences
end recurrence.

Do not rewrite past completed bookings.

================================================================
16. WAITLIST
================================================================

If enabled and a slot/class/resource is full:

customer can join waitlist.

Store:

desired service/resource
preferred date/time
customer
priority/order
expiry where applicable.

When availability appears:
offer the slot according to configured policy.

Do not silently confirm without customer acceptance unless the owner explicitly
uses such a policy.

================================================================
17. HOLDING A SLOT
================================================================

Where payment/deposit is required:

booking may temporarily HOLD the slot.

Example:

customer chooses 3:00 PM
→ slot held
→ payment link
→ payment confirmed
→ booking confirmed.

If payment is not completed within the hold window:
release the slot.

The current canonical AI Receptionist design already expects temporary holds to
expire. 

================================================================
18. DEPOSIT / FULL PAYMENT
================================================================

Use the Payments module.

Booking only stores:

what amount is required
what payment condition must be satisfied.

The Business may choose:

no payment
deposit
advance
full payment.

Examples:

Salon:
₹200 deposit.

Hotel:
one-night deposit.

Consultation:
full payment.

Restaurant table:
no payment.

Do not duplicate payment logic in Bookings.

================================================================
19. RESCHEDULE
================================================================

Customer/staff can reschedule according to Business policy.

Reschedule should:

check new availability
lock new slot
move booking
release old slot
preserve history
send updated confirmation/reminder.

Do not overwrite history silently.

================================================================
20. CANCELLATION
================================================================

Cancellation follows Business policy.

When allowed:

cancel booking
→ release slot/resource
→ payment/refund flow if applicable
→ customer notified
→ waitlist may react.

AI/WhatsApp cannot bypass the owner's cancellation rule.

Staff override requires permission/audit.

================================================================
21. NO-SHOW / ARRIVAL
================================================================

Where useful, support simple operational states:

confirmed
arrived
in_service / seated / checked_in where mode requires it
completed
cancelled
no_show.

Do not overload the booking record with unrelated operational detail.

Queue, attendance, housekeeping, jobs etc. remain separate modules.

================================================================
22. WHATSAPP BOOKINGS
================================================================

WhatsApp should use the same Booking service.

Typical structured path:

Service
→ date
→ slot
→ confirm.

Free-text example:

"Haircut tomorrow evening with Priya"

→ understand request
→ check real availability
→ offer suitable slots
→ customer confirms
→ same booking record.

Nothing is booked silently.

The canonical source explicitly says every WhatsApp booking ends in the same
LOCAH booking the Website would create. :chatgpt-content-reference{index="2"}

================================================================
23. PHONE / AI RECEPTIONIST
================================================================

AI Receptionist may:

check availability
hold slot
create booking
reschedule
cancel
send WhatsApp confirmation

within Business rules.

It should:

identify itself
use real availability
confirm the chosen slot
link AI-created booking to call/audit trail.

Anything outside its permissions:
handoff to staff.

The source already requires AI-created bookings to preserve actor/audit identity
and prevents two callers from taking the same slot. 

================================================================
24. FRONT DESK / STAFF
================================================================

Staff need a fast calendar/workflow.

They should be able to:

see today
see provider/resource schedule
find next available slot
create booking
move booking
cancel
mark arrival/no-show
contact customer
collect payment/deposit where applicable.

Do not make front-desk staff operate through the customer Website.

================================================================
25. ROLE-SPECIFIC EXPERIENCES
================================================================

Owner/Manager:
calendar across Business
utilization/availability
exceptions
no-shows
provider load.

Front desk:
today + next available + arrivals + waiting.

Provider:
my schedule only.

Teacher/trainer:
my classes/sessions.

Sales executive:
my site visits.

Housekeeping does not need Booking management; it gets Tasks triggered from
stays.

Same booking backend.

Different view.

================================================================
26. REMINDERS
================================================================

Use shared Automation kernel.

Examples:

booking tomorrow
booking in 2 hours
payment/deposit incomplete
waitlist opening
reschedule confirmation
cancellation confirmation.

Owner controls applicable reminder rules.

No duplicate reminders.

================================================================
27. MY ACTIVITY
================================================================

Customer should see applicable bookings in one LOCAH customer experience:

Upcoming
Past
Cancelled.

Allow appropriate:

view details
reschedule
cancel
pay balance
directions/contact
join/arrival information where configured.

Same real Booking record.

================================================================
28. WEBSITE SPECIALIZATION
================================================================

The Website booking UX should adapt.

Salon:
service → stylist → date → time.

Clinic:
department/provider → date → time.

Restaurant:
date → time → party size.

Hotel:
check-in/out → guests → room.

Gym:
trial/PT/class.

Real estate:
project → site visit.

Rental:
asset → date range.

Do not show one generic:

"Choose booking type / enter start / enter end"

form to everyone.

================================================================
29. BOOKING DOES NOT OWN EVERYTHING
================================================================

Keep module boundaries clean.

Booking owns:
reservation of time/resource/provider/capacity.

Payments owns:
money.

Memberships owns:
eligibility/session balance.

Queue owns:
walk-in waiting.

Attendance owns:
check-in.

Tasks owns:
housekeeping/prep.

Jobs owns:
actual service work.

Leads owns:
sales relationship.

Documents owns:
forms/waivers/guest documents.

This keeps Bookings simple and reusable.

================================================================
31. FINAL PRINCIPLE
================================================================

Bookings should feel ordinary and intuitive to the customer.

Pick what you want.
See real availability.
Choose a time/date/resource.
Pay if required.
Confirm.
Get reminders.
Reschedule/cancel according to policy.

The complexity stays inside LOCAH.

One Booking engine.

Very different experiences for:

appointment
table
stay
class
rental
site visit
event date.
